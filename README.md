# CPA-Helper — Public Runtime Snapshot

This public repository contains a sanitized snapshot of the deployed CPA-Helper runtime and locally maintained integration tools.

Upstream project: [walkingddd/CPA-Helper](https://github.com/walkingddd/CPA-Helper). The upstream MIT license and attribution are retained in `LICENSE`.

This is not the complete backend or frontend source tree: the backend is a prebuilt Linux AMD64 binary, and the frontend includes compiled assets. Maintained source for the mux and Codex setup tools is included. See the upstream project for its full source.

This repository starts with a clean publication history. Private deployment history, credentials, databases and user data are not included. Historical frontend files now obtain optional Hermes routing from deployment-only `runtime-settings.js`; no private route token is embedded.

Included:

- `dist/`: current frontend build served by CPA-Helper
- `cpa-helper-linux-amd64`: CPA-Helper backend binary
- `cpa-mux`: local mux/proxy binary used for Hermes compatibility
- `start-with-mux.sh`: startup script used by the deployment override

Excluded intentionally:

- SQLite database files
- runtime logs
- API keys and Hermes secret files
- backup HTML files created during hotfixes

Notes:

- This is a deployment snapshot, not the original source tree.
- The current entrypoint loads `dist/assets/index-cpa-setup-20261117.js`.
- The API keys page uses `dist/assets/ApiKeysView-codex-setup-20261117.js`.

## Claude-client model aliases

The mux pins genuine Claude routes to CPA's Antigravity provider and exposes
GPT-5.6 Sol through a separate Claude-client-compatible ID. Rewriting happens
only on Anthropic Messages requests (`POST /v1/messages`):

- `claude-sonnet-4-6` -> Antigravity Claude Sonnet 4.6
- `claude-opus-4-6` -> Antigravity Claude Opus 4.6
- `claude-opus-4-6-thinking` -> Antigravity Claude Opus 4.6 Thinking
- `claude-opus-4-8` -> `gpt-5.6-sol` (repurposed supported client slot)

On startup, `start-with-mux.sh` reads the already configured CPA management key
from CPA-helper's local database and reconciles provider-unique OAuth aliases
under the `antigravity` channel. Existing unrelated Antigravity aliases are
preserved. The public Claude IDs are then rewritten to those private aliases,
so CLIProxyAPI cannot choose Codex merely because both providers expose the same
public model name. Stale persisted mappings that attempt to redirect canonical
Claude IDs to GPT are rejected automatically. Because the client accepts only a
fixed model-ID allowlist, the supported `claude-opus-4-8` slot is intentionally
repurposed for GPT-5.6 Sol and no longer targets native Opus 4.8.

For Claude clients that keep `claude-opus-4-6` as the model ID, an enabled or
adaptive Anthropic `thinking` request option is detected before aliasing and is
routed to `claude-opus-4-6-thinking`; disabled or absent Thinking remains on
native `claude-opus-4-6`.

For `claude-sonnet-4-6` on Anthropic Messages, the mux removes adaptive
`thinking` and effort controls before forwarding to CPA. Claude Desktop adds
those controls automatically, but Antigravity may exhaust the effort-specific
route while the same OAuth credential still serves plain Sonnet requests. This
normalization is limited to Sonnet Messages requests; Chat Completions clients
such as Workbuddy and Opus Thinking routes are unchanged.

The production Zeabur service exposes the mux on port `18317` and reaches CPA
through the existing public gateway because the old deployment's private DNS is
not visible in this project. Sonnet Messages requests are bridged through CPA's
Antigravity Chat Completions route and converted back to Anthropic response
events, avoiding the provider ambiguity in CPA's native Messages route.

The Claude Code setup command generated by the API-key page configures only the
gateway URL and token. It deliberately does not set `ANTHROPIC_MODEL`,
`CLAUDE_CODE_SUBAGENT_MODEL`, or a fixed `claude --model` argument, so model and
Thinking selections made in Claude Code can reach the mux unchanged.

Production deployment note: the service must build from this repository's
root so the bundled runtime binaries and `dist/` assets are in the Docker
build context.

`HERMES_TOKEN` and `HERMES_API_KEY` are optional. When they are absent, the
tokenized Hermes route is disabled while the standard authenticated `/v1`
routes remain available.

## Codex setup commands (2026-11-17)

The live API-key page uses `ApiKeysView-codex-setup-20261117.js` and the
`cpa-codex-setup-20261117.js` command generator. Mac and Windows each support
basic API-key login, a custom CPA provider, and account restoration. The command
downloads a versioned script and verifies its SHA-256 before running it.

Scripts validate the model catalog and a streaming Responses request before
closing the desktop app or writing configuration. They preserve unrelated TOML
settings, save account credentials for restoration, and use file backups and
atomic writes. They do not patch application archives or clone conversation
history. Open a new chat after switching. Mac requires Python 3; Windows uses
Windows PowerShell. Configurations containing TOML multiline strings are
rejected before modification and require manual merging.

Maintained sources and regression tests are in `tools/codex-setup/`. Run
`python3 tools/codex-setup/build.py` to regenerate the versioned assets.
`test_setup.py` exercises both platforms against a local mock endpoint, with
PowerShell 7 on macOS for configuration logic. Actual Windows desktop restart
still requires verification on Windows. Production scripts were tested against
the live endpoint, and a separate Codex CLI session completed through CPA.

The deployment changes only persistent frontend assets and the HTML entrypoint.
Original assets remain available for rollback. Production entrypoint backup:
`/app/data/override/backups/codex-setup-20261117175938/index.html`.
